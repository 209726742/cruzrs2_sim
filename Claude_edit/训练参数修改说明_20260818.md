# π0.5 训练脚本参数修订说明

> 修订时间：2026-08-18
> 影响文件：`cruzr_mujoco_sim/scripts/training/pi05_formal300_train.sh`（重写）、`pi05_train.sh`（两行补丁）
> 触发原因：50-source step-1000 checkpoint 在 seed 6 闭环为 0 grasp / 0 placed；在启动 300-source 长训前复查全部训练参数
> 目标硬件：2×H100 80GB，训练预算 1–2 天

---

## 一、一句话结论

参数本身大多是对的（基本照搬 openpi 的 π0.5 配置），但**有效 batch size 只有 4，比 openpi 官方 recipe 小 64 倍**，导致 10k 步训练累计只见过约 1.2% 的训练帧。这一条足以单独解释闭环 0 grasp，不需要用"长时序学习困难"来解释。本次修订围绕这个问题，外加一个学习率排程的配置错误。

## 三、逐条理由

### 1. 有效 batch：4 → 32（最重要的一条）

`--batch_size` 是**每个 DDP 进程**的 batch，有效 batch = `BATCH_SIZE × NUM_PROCESSES`。你们的 canary 日志也是这么记的："有效 batch size 为 4（1/GPU × 4）"。

算一下 10k 步训练到底见了多少数据：

```
10,000 步 × 有效 batch 4 = 40,000 个样本
train split 帧数 = 3,330,327
覆盖率 = 40,000 / 3,330,327 ≈ 1.2%
```

对照 openpi 官方的 π0.5 微调 recipe：**batch size 256，30,000 步**，累计 768 万样本。你们差了 190 倍。上一轮 50-source 的 step-1000 更极端，累计只有 4,000 个样本。

三个独立证据都指向同一结论：

**证据 A — 梯度被砍掉 96–98%。** canary 记录的 grad norm 是 25.5 / 33.7 / 20.2 / 42.0，而 `grad_clip_norm=1.0`。每一步都只保留梯度方向、丢掉全部幅度信息。这是 batch 太小、梯度估计被 flow matching 的噪声采样与时间步采样方差主导的典型特征——不是模型有问题，是每步的梯度信噪比太低。

**证据 B — GPU 几乎在空转。** 4090 上 1.0–1.14 s/step 只处理 4 个样本，约 0.9 样本/秒/卡。π0.5 在 `train_expert_only=true` 下骨干冻结、以前向为主，4090 的合理吞吐应该在 5–10 样本/秒/卡这个量级。batch=1 时大部分时间花在 kernel launch 和小矩阵乘法上，算力利用率是个位数百分比。**换句话说，提高 batch 的边际成本远低于线性——batch 从 1 提到 16，step 时间大概只会涨 2–4 倍，但每步的工作量涨 16 倍。**

**证据 C — 显存根本没用满。** canary 实测 15.5 GiB/卡，而这几乎全是固定开销：bf16 权重 4.143B × 2 B ≈ 8.3 GB，加上 693M 可训练参数的 AdamW 状态（fp32 的 m 和 v，693M × 8 B ≈ 5.5 GB），合计约 13.8 GB。也就是说 batch=1 时激活占用不到 1 GiB。H100 80GB 减去这 15.5 GiB 固定开销还剩约 60 GiB，全部可以拿来放激活。

> **特别注意**：如果换到 2×H100 后不改 `BATCH_SIZE`，有效 batch 会从 4 掉到 **2**，比现在更糟。这是本次把默认值直接改掉、而不是只写在文档里的原因。

新默认值 `BATCH_SIZE=16 × NUM_PROCESSES=2 = 32`，配合 30k 步 → 96 万样本 ≈ **28.8% 训练帧覆盖**。`plan` 动作会把这个数字直接打出来。

### 2. `scheduler_decay_steps` 与 `steps` 不匹配

旧的 `pi05_formal300_train.sh` 里**根本没有传** `--policy.scheduler_decay_steps`，走 LeRobot 的 `PI05Config` 默认值 30000（这个默认值来自 openpi，那边 `num_train_steps` 也确实是 30000）。但你们的 `steps=10000`。

余弦退火的进度是按 `decay_steps` 算的：

```
progress = (10000 - 1000) / (30000 - 1000) = 0.31
cos 因子 = 0.5 × (1 + cos(0.31π)) ≈ 0.78
```

训练在这里就停了，**学习率结束时仍在峰值的约 80%，完全没有退火收尾阶段**。对 flow matching 策略来说，末段低学习率的精调通常贡献很大一部分最终性能，这一段被整个跳过了。

修订后 `DECAY_STEPS` 默认 `= TARGET_STEPS`，并且新增 `validate_schedule()`：两者不一致时会打印明确警告（有时你确实想故意不一致，所以是警告不是硬错误）。

### 3. 有效 batch 下限保护

新增 `MIN_EFFECTIVE_BATCH=16`，`start` 时如果有效 batch 低于这个值就直接拒绝启动，并提示先跑 `sweep`。

理由很直接：这个错误已经悄无声息地毁掉了一轮训练，而它在日志里完全看不出异常——loss 在降，没有 NaN，没有 OOM，checkpoint 能复载，所有验收项全绿。只有闭环评测才暴露问题，而那时已经花掉了几个小时。**保护的价值在于它拦的是"看起来一切正常"的失败。**

要复现旧实验时设 `ALLOW_SMALL_BATCH=1` 显式放行。

### 4. 优化器 / scheduler 超参全部显式传入

旧脚本一个优化器参数都没传，全靠 LeRobot 的 `PI05Config` 默认值。这有三个问题：

- **改不了**：想调学习率就得改源码或换脚本，而这正是问题 2 存在的原因；
- **不可追溯**：`train_config.json` 里记的是默认值，升级 LeRobot 后同样的命令可能跑出不同的训练；
- **resume 会继承**：`resume` 走 `--config_path=<ckpt>/train_config.json`，任何默认值都会一路继承下去。

现在显式传入 7 个：`optimizer_lr`、`optimizer_weight_decay`、`optimizer_grad_clip_norm`、`scheduler_warmup_steps`、`scheduler_decay_steps`、`n_action_steps`、`num_inference_steps`。

这 7 个是根目录 `pi05_train.sh` 已经在用的，可以确认你们这版 LeRobot 支持。**没有加 `scheduler_decay_lr` 之类未经确认的参数**——宁可少传也不要传一个会让 argparse 直接报错的 flag。

数值全部保持 openpi 的 π0.5 默认（lr 2.5e-5 / wd 0.01 / clip 1.0 / warmup 1000），只有 `decay_steps` 改成跟随步数。**学习率没有跟着 batch 一起放大**，因为 2.5e-5 本来就是为 batch 32 量级调的——之前是 batch 太小配了个偏大的学习率，现在正好对上。

### 5. `TARGET_STEPS`：10000 → 30000

对齐 openpi 的 π0.5 微调 recipe（30k 步）。按 2×H100、有效 batch 32、每步 1.5–3 s 估算，30k 步大约 12–25 小时，落在 1–2 天预算内。

实际 step 时间必须以 `sweep` 的实测为准；如果比预期慢，用 `TARGET_STEPS` 调整即可。

### 6. `NUM_WORKERS`：2 → 8

batch=1 时每步只需要解码 3 路视频帧，2 个 worker 绰绰有余（canary 实测 `data=0.004 s`）。batch 提到 16 之后每步要解码 48 帧，DataLoader 会立刻变成瓶颈。

8 是个保守起点。跑起来后如果日志里的 `data_s` 明显不为 0，就往上加到 12–16；上限看机器 CPU 核数（建议不超过 `核数 / NUM_PROCESSES`）。

### 7. `SAVE_FREQ`：500 → 1000

单个 checkpoint 约 11 GiB。30k 步按 500 存会产生 60 个、约 660 GiB，而且每次写 11 GiB 都会打断训练。1000 步一存 → 30 个、330 GiB，断电最多重算 1000 步（约 25–50 分钟）。存储余量 6.2 PiB 不是约束，写盘时间才是。

### 8. `resume` 不再静默从头开始

旧逻辑：`resume` 时如果找不到完整 checkpoint，就归档现有输出并**从基础权重重新开始训练**。

在 20 步 canary 的场景下这没问题。但在一个跑了 20 小时的长训里，如果因为某种原因（比如 checkpoint 校验失败）识别不到进度，这个逻辑会静默地把一切推倒重来，而你从命令输出里很难第一时间意识到。

改为默认拒绝并打印检查建议，确认要重来时设 `ALLOW_RESTART_FROM_BASE=1`。

### 9. `--multi_gpu` 条件化

旧脚本无条件传 `--multi_gpu`。`NUM_PROCESSES=1` 时 accelerate 会拒绝启动。想单卡调试就得改脚本。小问题，顺手修掉。

### 10–11. 新增 `plan` 和 `sweep`

**`plan`** 不启动任何进程，只打印完整配置 + 从 `meta/info.json` 估算的训练帧覆盖率。用它可以三秒钟看出"这次训练到底会见到多少数据"。旧配置跑一下会直接显示 `1.2%`——这个数字如果当初就打在启动日志里，问题不会拖到闭环评测才暴露。

**`sweep`** 在多档 batch 上各跑一次短训练（默认 `8 16 32`，各 40 步，不保存 checkpoint），后台采样 `nvidia-smi` 并报告每卡峰值显存和最后几行 step 时间；某一档 OOM 就停下，更大的不再试。

注意每档都是一次完整冷启动（4250 episodes 索引 + 4.14B 权重加载），单档十几分钟，三档接近一小时。只想确认单个值时用 `SWEEP_BATCH_SIZES="16"`。

### 12. `RUN_TAG`

旧脚本的输出目录、日志名、job 名都硬编码了 `_20260817` / `_10k`。换硬件或换 batch 重跑时，`canary` 会看到旧的 step-40 checkpoint 直接返回"已完成"，实际上那是 4090 batch=1 的验证结果，对新配置毫无意义。

现在统一带 `RUN_TAG`（默认 `h100x2`），不同配置的产物天然隔离。

## 四、破坏性变更 / 迁移说明

**默认输出目录变了。** 旧的 `pi05_formal300_v24_10k_20260817` 和 `..._ddp_canary_20260817` 不再是默认路径。现有的 canary step-40 checkpoint 保持原样、不受影响，但新脚本不会去找它。

**要恢复旧路径上的训练**，显式指定即可：

```bash
FORMAL_OUTPUT=cruzr_mujoco_sim/out/training/pi05_formal300_v24_10k_20260817 \
FORMAL_JOB_NAME=pi05_formal300_v24_10k \
TARGET_STEPS=10000 GPU_IDS=0,1,2,3 NUM_PROCESSES=4 BATCH_SIZE=1 \
bash cruzr_mujoco_sim/scripts/training/pi05_formal300_train.sh resume
```

**换 batch size 必须开新的输出目录，不能 resume。** `resume` 走 `--config_path=<ckpt>/train_config.json`，会连同 batch、workers、scheduler 一起继承 checkpoint 里的配置。想用新 batch 就得从基础权重重新开始——这也是为什么建议在启动长训**之前**把 batch 定下来。

**脚本未经你们真实环境验证。** 我这边做了 `bash -n` 语法检查，并用桩化的 `nvidia-smi` / python 跑通了 `plan`、`start` 拦截、`resume` 拦截、`help` 这几条路径。但没有真实 GPU、没有真实数据集、没有 LeRobot。落地后请按第六节的顺序先跑 `plan` 和 `sweep`。

## 五、对 `pi05_train.sh` 的最小补丁

根目录的通用启动器已经暴露了全部参数，只有一个同类问题：`DECAY_STEPS` 固定 30000，与 `TARGET_STEPS` 解耦。改两行：

```diff
 TARGET_STEPS=${TARGET_STEPS:-10000}
 ...
-DECAY_STEPS=${DECAY_STEPS:-30000}
+# 默认跟随目标步数，避免学习率排程跨度大于实际训练长度导致退火不完整
+DECAY_STEPS=${DECAY_STEPS:-$TARGET_STEPS}
```

注意 `DECAY_STEPS` 的定义要在 `TARGET_STEPS` 之后（当前文件里 `TARGET_STEPS` 在"主要训练配置"段、`DECAY_STEPS` 在"优化器"段，顺序已经是对的）。

另外建议在 `validate_common_config()` 里补一句一致性检查：

```bash
if (( DECAY_STEPS != TARGET_STEPS )); then
  printf '警告：DECAY_STEPS=%s 与 TARGET_STEPS=%s 不一致，学习率不会在训练结束时退到底\n' \
    "$DECAY_STEPS" "$TARGET_STEPS" >&2
fi
```

## 六、建议的执行顺序

```bash
# 0. 语法自检
bash -n cruzr_mujoco_sim/scripts/training/pi05_formal300_train.sh

# 1. 看配置和覆盖率，不启动任何东西
bash cruzr_mujoco_sim/scripts/training/pi05_formal300_train.sh plan

# 2. 实测 H100 上每卡能放多大 batch（约 1 小时）
bash cruzr_mujoco_sim/scripts/training/pi05_formal300_train.sh sweep

# 3. 用 sweep 选出的 batch 跑 20 步 canary，验证 DDP + checkpoint
BATCH_SIZE=<选定值> bash cruzr_mujoco_sim/scripts/training/pi05_formal300_train.sh canary
BATCH_SIZE=<选定值> bash cruzr_mujoco_sim/scripts/training/pi05_formal300_train.sh canary-resume

# 4. 启动正式训练
BATCH_SIZE=<选定值> bash cruzr_mujoco_sim/scripts/training/pi05_formal300_train.sh start

# 5. 监控
bash cruzr_mujoco_sim/scripts/training/pi05_formal300_train.sh status
tail -f log/pi05_formal300_h100x2.log

# 6. 重启后恢复（BATCH_SIZE 会从 checkpoint 自动恢复，无需再传）
GPU_IDS=0,1 NUM_PROCESSES=2 bash cruzr_mujoco_sim/scripts/training/pi05_formal300_train.sh resume
```

选 batch 的标准：峰值显存 ≤ 单卡显存的 85%（H100 80GB 即 ≤ 约 68 GiB），留出碎片和峰值波动的余量。

另外在 H100 上值得单独试一次 `GRADIENT_CHECKPOINTING=false`：80GB 显存下中等 batch 可能放得下，能白捡 20–40% 的速度。放不下就退回 `true`。

## 七、本次没有改、但需要知道的

### `train_expert_only=true`（保持）

现在只训练 693M / 4.14B 参数，PaliGemma 骨干完全冻结、从没适配过 MuJoCo 渲染和 18 维 state。这是"为什么抓不到"的嫌疑人 #2。

首轮不动它，因为：batch 的缺口是 8–64 倍量级，而解冻骨干只是"可能有帮助"；而且解冻后 AdamW 状态从 5.5 GB 涨到约 33 GB，为了塞下又得把 batch 压回去，两个改动会互相抵消、还没法归因。留作第二轮的对照实验。

### `n_action_steps=50`（保持，但评测时要改）

在 LeRobot 里 `chunk_size` 是训练时预测的动作长度，`n_action_steps` 是推理时**开环执行多少步**才重新规划。改它**不影响训练**，只影响 rollout。

50 步 @ 30 fps = 1.67 秒全开环执行，对接触丰富的抓取偏激进。闭环评测时试 `n_action_steps=10~25`（执行 chunk 的 20%–50%），成本为零，可能直接改变 grasp 结果。**这是现在就能做的、最便宜的一个变量。**

### `eval_freq=0`（保持）

LeRobot 的 `eval_freq` 需要挂在线环境，你们的闭环评测走独立的 rollout 脚本。保持关闭，改为在 5k / 10k / 20k / 30k 这几个 checkpoint 上做离线闭环评测。

不要只看 loss 判断成败——这一点你们的进度文档里已经写对了。

### EMA

openpi 的 π0.5 配置带 `ema_decay=0.999`，LeRobot 的训练入口默认没有 EMA。值得确认一下你们这条代码路径有没有；没有的话是个已知差距，通常会损失几个百分点，但不是 0 grasp 的原因。

### 30 fps 与任务时长

`4,128,148 帧 / 300 条源 ≈ 13,760 帧/条`，30 fps 下**每条源 episode 约 7.6 分钟**，而 action chunk 只有 1.67 秒。

两个值得查的点，优先级不低于任何超参：

1. **语言条件的粒度**：如果整条 7.6 分钟 episode 的每一帧共用同一句全局任务描述，模型无法知道自己处在"导航 / 对准 / 抓取 / 放置"哪个阶段。π0.5 的设计本来就依赖 high-level subtask 条件解决这个问题。请确认数据集构建时 task 字符串是否随阶段变化。
2. **抓取帧占比**：7.6 分钟里真正的接触/抓取可能只有十几秒。均匀采样下抓取帧占比可能不到 5%，batch 再大也是在反复学导航。加权采样或专门的 manipulation 子集，收益可能超过任何调参。

下一轮数据集可以考虑把控制频率降到 10–15 Hz：同样 50 步的 chunk 能覆盖 3.3–5 秒，长时序压力小一个量级，帧数也减少 2–3 倍。需要重建数据集，不适合塞进这次的训练窗口。

### 启动长训前先做的诊断（强烈建议）

用现有的 50-source step-1000 checkpoint，在它**训练集里见过的 seed** 上跑一次闭环：

- 连见过的 seed 都 0 grasp → 是拟合/表示问题（归一化、动作空间、chunk、prompt 粒度），这时候堆算力没用；
- 见过的能抓、seed 6 抓不到 → 是覆盖/泛化问题（场景 sweep 只有 16/26，低于自定的 24/26 门槛）。

成本几十分钟，但直接决定这 1–2 天该怎么花。
