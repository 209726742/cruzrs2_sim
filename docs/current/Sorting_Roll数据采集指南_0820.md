`sorting_roll_v9_d405_sim`：三路 RGB 以 30 FPS 同步保存，深度仅保留为可选辅助数据，
不输入 π0.5；棒子和货架尺寸在没有实测值前明确标记为仿真候选，不能冒充真机标定值。

不得浮空；松手后连续稳定至少 `2 s`；双手完全撤回；总仿真时长不超过 `60 s`。
无扰动基准已在 `58.25 s` 内通过；最终连续复测 seed 3–7 为 `5/5`。正式动力学门

`56.233–58.800 s`。下一阶段才渲染并验收 `30–50` 个 canary、构建 LeRobot 数据集

当前旧 `dev026–dev069` 及重复帧/诊断缓存已经清理；文档后文出现的这些路径只保留为

## 2026-08-23 双腕 RealSense 候选

### 三个互补专业视角

- **机器人操作与可观测性**把问题定义为“关键接触状态是否可见”，推荐一个全局视角分别配合左右腕近景；它提醒数据工程不要用“有画面”代替“看得到对应棒端、指尖和槽边”。如果真机画面显示腕部长期自遮挡，它会否决当前挂载。
- **π0.5 数据合同**把问题定义为“相机字段在训练与部署时是否保持同一语义”，推荐独立的 `sorting_roll_realsense_candidate_v1`，禁止把旧腰部/底盘画面和真腕画面混在同名字段中；它提醒机械视角不要忽略时间同步和数据版本污染。如果相机消融训练证明腕部视角没有收益，它会接受更少视角。
- **真机系统可靠性**把问题定义为“两台 USB 相机在运动、重启和长录制中是否仍可识别、同步且不碰撞”，推荐序列号绑定、刚性支架、线缆检查和短 pilot；它提醒仿真与学习视角不要把代理外参当成实物。只有带真实序列号、`CameraInfo` 和压力测试的证据才能让它批准批采。

三者共同认可：一个全局视角不可缺，左右腕必须提供互补证据，正式采集前必须验证同步和遮挡。分歧在于仿真结果能否直接决定真机安装；背后的不同假设是“仿真代理外参足够接近”与“真实支架、镜头和线缆误差会主导结果”。因此仿真只筛掉明显失败方案，真机 pilot 才能转正。

### 第一性原理约束

- **已确认事实**：本仓库 π0.5 接受多路 RGB 并缩放到 `224×224`；当前数据为 `30 FPS`，相机—状态最大时间差为 `20 ms`；CRUZR SDK 没有原生腕部 RGB；当前成功轨迹和物理成功证据已经存在。
- **未验证假设**：RealSense 型号、焦距、最低工作距离、真实支架外参、USB 带宽和腕部运动模糊均未知；仿真左右代理挂载不对称，不能据此制造支架。
- **目标**：全局画面负责桌面、移动和架体关系，左右腕分别看清自身指尖、对应棒端及一体式顶层槽边；三路与状态/动作严格同步，并在训练和部署时保持完全相同的语义。
- **资源与约束**：当前单张 4090 足以完成回放、可观测审计和 pilot；没有真实相机流时不能验证硬件，也不能把候选标记为 `training_eligible=true`。

### 综合方案与仿真证据

- **推荐方案**：`observation/image → stereo_left`，`left_wrist_image → left_wrist_realsense`，`right_wrist_image → right_wrist_realsense`。候选配置与正式 SDK 合同隔离，旧数据不得直接混入。
- **仿真结果**：角色化审计覆盖 18 个关键阶段、每阶段首中末共 54 个样本；全局负责整棒与整体槽位，左右腕分别检查自身手部、局部棒子接触点和对应槽边。最终候选所需角色覆盖 `54/54`，平均有效视角 `2.81`。
- **适用条件**：仅用于选择真机安装方向和检查采集合同；当前腕部视角来自历史诊断相机的代理几何，右腕光轴由成功轨迹搜索得到，尚不是任何具体 RealSense 型号的标定值。
- **最大风险**：真实支架与镜头导致自遮挡、运动模糊、USB 丢帧或线缆碰撞；其次是把旧的腰/底盘“腕部槽位”数据与新真腕数据混用。
- **退出条件**：任一关键阶段对应棒端、指尖或槽边连续不可见；左右流重复/互换；30 FPS 长录制不稳定；相机—状态偏差超过 `20 ms`；支架或线缆限制关节运动。任一触发即停止正式采集并返回安装设计。
- **第一步行动**：真实相机到位后，在不采训练数据的前提下固定机器人于观察、夹持、架前对准、释放四个姿态，录制三路同时时间戳画面；通过视野、序列号、同步和碰撞检查后再录 3–5 个完整 pilot。

## 2026-08-22 相机第一性原理审计

### 已确认事实

- 原始 CRUZR S2 SDK 列出 `chassis_front / waist_front / fisheye_left / fisheye_right / stereo_left / stereo_right` 六路 RGB 端点，没有左右腕部 RGB 相机；`left_wrist_image / right_wrist_image` 只是 π0.5 兼容槽位名。
- `dev071` 当前四路机器人相机都能对应 SDK 端点，运行时安装父级、位置和光轴门通过；但 `intrinsics_verified=false`，统一 `70° FOV` 仍是等待真机 `CameraInfo` 替换的仿真假设。
- 当前正式映射是 `stereo_left / waist_front / chassis_front`，`stereo_right` 只作评审；历史 ECU smoke 使用过 `stereo_left / stereo_right / waist_front`。二者尚未经过同任务对照，不能默认等价。
- 当前主机没有可用的 `ros2` 命令或真机相机流，因此只能证明 SDK 文档与仿真资产一致，不能证明这一台真机的六路端点都已安装、启用和同步。

### 可重复审计方法

- 新增 `scripts/collection/sorting_roll_camera_audit.py`，从 `episode_data.npz` 精确恢复双臂、夹爪、底盘和棒子位姿，再以 MuJoCo 对象分割在 π0.5 的 `224×224` 分辨率测量棒子无遮挡投影、实际可见面积、轴向跨度及目标层三个关键点是否入画。
- 审计覆盖观察、接触抓取、运输、架前对准、层内送入和释放确认共 `18` 个阶段；每阶段取首、中、末三帧，共 `54` 个关键采样点。该门只用于拒绝明显不可观测的组合，通过不等于已经证明 π0.5 可学习。
- 报告保存在 `output/sorting_roll_expert/v8_candidate_dev071/camera_observability.json`；完整任务在 tmux 中完成，输出日志为同目录 `camera_observability.log`。
- 三路候选合成视频为同目录 `sorting_roll_policy_candidate_multiview.mp4`，已验证为 `960×540 / 30 FPS / 2106 帧 / 70.2 s`，只用于视角评审。

### dev071 结果与决策

- 当前三路 `stereo_left / waist_front / chassis_front` 覆盖 `54/54` 个关键点，但平均只有 `1.0` 路有效操作视角；实际上全部有效操作证据都来自左目。
- `stereo_left / stereo_right / waist_front` 同样覆盖 `54/54`，平均有 `2.0` 路有效操作视角；左右双目都能看到棒子、两端方向跨度和最终目标层。
- 四路全开仍只有平均 `2.0` 路有效操作视角，说明底盘相机没有增加棒子抓取或落槽的观测冗余，只增加约 25% 的图像渲染、写盘和视觉编码开销。
- 腰前与底盘相机在全部关键阶段的棒子无遮挡投影均为 `0` 像素，但都能看到桌子或货架，作用属于导航上下文而非精细操作。人工复核显示底盘相机常被过近桌腿或层板裁切，腰前视角保留的机器人—目标整体关系更完整。
- 因此无外接腕相机时，仿真侧 SDK-only 三路候选为 `stereo_left / stereo_right / waist_front`；它是成本敏感的退路，不是正式冻结。若安装双腕 RealSense，则按上一节的独立候选 profile 评审。不得在获得真机话题、`CameraInfo`、实拍停车位画面和时间同步证据前修改正式契约或开始批量采集。
- 当前 `dev071` 继续保持 `training_eligible=false`。下一准入步骤是真机同停车位相机审计；若真机暂不可用，只允许用当前四路原始数据做小规模相机消融 canary，不允许把第三视角、槽位近景或虚构腕部相机送入策略。

## 2026-08-22 实物参考图纠偏：目标槽属于货架本体

### 1. 已确认、无法绕开的基本事实

- 三张实物图显示：每一层由穿孔背板、向前收拢的底部承托区和前侧挡边共同组成；橡胶棒落在层板内部最低处，目标槽不是架体外另装的 U 形件。
- 当前编译后货架视觉网格的世界坐标前边界约为 `X=0.799875 m`，旧目标中心却是 `X=0.7825 m`。旧目标位于视觉货架外侧，这直接解释了旧视频里“棒子看似浮在架外”的现象。
- 对现有货架网格做中心截面求交后，顶层前挡边约位于 `X=0.926–0.943 m, Z=0.882–0.912 m`，最低承托区约在 `X=0.941–0.957 m, Z≈0.888 m`，后斜板由此延伸到约 `X=1.033 m, Z=0.948 m`。旧目标比真实承托区约前移 `167 mm`、高出 `112 mm`。
- 现有视觉网格已经包含一体式层板外形；正确实现不应再添加蓝色/异色目标槽，只需用默认不可见的简化碰撞体贴合网格截面。

### 2. 习惯性接受、却没有验证过的假设

- 把“槽宽 25–30 mm”直接解释为独立 U 形导槽，而没有先从实物图确认层板拓扑。
- 认为可见槽与碰撞槽数值相同就足够；二者即使同源，只要整体都建在货架外，仍是同一个错误被重复表达。
- 用水平 `shelf_tier4_col` 代表顶层底面，却没有对视觉网格做截面审计；该平面实际穿过一体式篮筐结构。
- 把“触碰后回中再释放”当成通用放置逻辑；它只是在修补错误的窄 U 槽，不适用于有前挡边和后斜板的真实层板。

### 3. 真正想实现的目标

- 棒子先完整越过顶层前挡边，进入货架内部，再在手指不碰架的前提下降到距一体式承托面不超过受控高度；随后同步张爪并抬手，让棒子以有界落差落入最低承托区，最后越过挡边再后撤。
- 成功必须同时证明：棒心位于层板内部、左右端均在立柱内侧、轴向正确、与一体式承托面真实接触、双手已释放且状态连续稳定。
- 正常视频只显示货架原有网格和棒子，不出现额外蓝槽，也不允许隐藏悬空碰撞面制造“物理成功”。

### 4. 现实中的资源与约束

- 当前单张 RTX 4090 足以完成几何、动力学、轨迹和单回合视频验证；几何尚未正确前使用 4/8 卡没有收益。
- 照片只能确认结构拓扑，不能提供局部毫米尺寸。现阶段以已按总尺寸缩放的货架网格截面为仿真基准，正式采集前仍需实测槽深、前挡边高度和顶层净宽。
- 观察、协调平抓和一次转向运输已有独立验证，可以保留；目标几何、架前送入/下放/释放和成功合同必须重做。
- 长回合继续只在 `tmux` 会话中运行，且用户批准新视频前保持 `training_eligible=false`，不进入多 seed 或批量采集。

### 原方案中只在修补表面的部分

1. 给错误的外挂碰撞槽补一套可见蓝色几何，只改善了观感，没有纠正目标拓扑。
2. 围绕 30 mm 窄槽反复调整轻触、回中和张爪时序，优化的是一个实物中不存在的约束。
3. 用碰撞体近景证明旧判定，而没有先检查目标是否位于货架视觉边界之内。

### 从基本事实重新推导出的新路径

1. 删除外挂 U 槽、顶层悬空水平面和旧横杆代理；保留原货架视觉网格。
2. 依据网格截面，用不可见碰撞体表达一体式前挡边、最低承托区、后斜板和后板，并先做静态落槽与多角度渲染。
3. 成功判定改为一体式层板内部包络、端点余量、承托面真实接触、完全释放和稳定时间的联合证据。
4. 在静态正反例通过后，先用实际夹爪外廓验证“持棒接触承托面”是否几何可行；若不可行，改为“高于挡边送入 → 层内安全下放 → 有界落差与手指净空确认 → 同步张爪/抬手 → 稳定落槽 → 后撤”，再用单 seed 低清 tmux 回合验证。

### 这条路径成立的前提

- 现有货架视觉网格的整体尺寸和姿态仍与实物场景一致；局部截面只是待实测校准的近似，而不是宣称已获得真实毫米尺寸。
- 简化碰撞体必须贴合视觉网格且默认不渲染，不能侵入层板外侧或生成视觉中不存在的支撑面。
- 双臂能够在保持棒子水平和四指腹夹持的情况下越过前挡边；若静态可达性或组合碰撞验证失败，应调整机器人/货架相对停车位，而不是放宽成功门。

### 验证它的第一步

先用更新后的场景把棒子从挡边上方静态释放：它必须自然落在顶层最低承托区、不会滚出前挡边，正常渲染中不出现外挂槽；随后故意把棒子放在货架外或悬空，成功判定必须拒绝。

### 综合后最推荐的方案

- **推荐方案**：原货架视觉网格 + 截面对齐的一体式隐藏碰撞 + 层内真实接触成功门 + “越挡边后下放”的双臂轨迹。
- **适用条件**：当前 MuJoCo 单卡专家验证阶段，且实物局部精确尺寸尚未补测。
- **最大风险**：低模网格的局部曲面与实物尺寸存在偏差，导致仿真可放而真机净空不足；第二风险是新目标更靠货架内部，现有双臂停车位可能不可达。
- **退出条件**：静态棒子不能稳定落在视觉承托区；碰撞体超出网格；正常/物理视图不一致；双臂越挡边时发生碰撞或无法完全脱指；任一条件触发都停止录像并回到几何或停车位设计。
- **第一步行动**：先完成场景几何、成功判定及静态正反例；在它们通过前，`dev069` 保持作废，不修改专家时序去适配未验证目标。

## 2026-08-22 第一性原理复盘与重推路径（历史阶段，已被本节部分证伪）

### 1. 已确认、无法绕开的基本事实

- CRUZR S2 SDK 原文给出六个 RGB 成像端点，没有腕部/手部相机。当前录制的 `stereo_left / stereo_right / waist_front / chassis_front` 确实是 MuJoCo 固定相机，并分别挂在机器人 `head_pitch_link / waist_yaw_link / chassis` 运动链上；录制器按相机 ID 使用 `mjCAMERA_FIXED` 渲染，不是拿自由第三视角冒充机器人相机。
- “挂在机器人上”不等于外参正确。SDK 腰前相机位置为父链接前方 `0.07754007 m`、上方 `0.02319591 m`、pitch `51°`；当前 XML 实际为前方 `0.130 m`，前移多了 `52.46 mm`，运行时光轴仅向下约 `35°`。头部双目虽然把任务头俯角烘焙进了光轴，却仍保留零位头姿下的位置，没有把相机位置绕 head-pitch 原点一起旋转。底盘相机的位置和 `-10°` pitch 与 SDK 表一致。四路 `fovy=70°` 没有真机 `CameraInfo` 佐证，只能标为待真机标定的仿真假设。
- `dev063` 的抓取准备不是自然的同步双臂动作。右臂和左臂由两个串行循环依次完成净空与预抓取，导致一只手已经横向伸展时另一只手仍垂下；“抬起并放平”耗时约 `10.97 s`，“水平预抓取”又耗时约 `14.63 s`。
- `dev063` 的物理落槽证据真实存在：槽底两个接触点、约 `2.448 N` 支撑力、棒底—槽底约 `-0.059 mm`、夹爪和桌面支撑力均为 `0 N`。但高精度货架视觉网格不参与碰撞，真正承托棒子的 `group 3` 槽体在正常第三视角默认隐藏；也就是说，棒子由一个视频里近似不可见的碰撞槽承托，正常视频看起来浮空是可复现的视觉—物理不一致，而不只是观看者误判。
- `dev063` 总时长 `95.283 s`。最大可删减块不是最后几毫米慢送，而是抓取前串行双臂准备约 `25.6 s`、架前逐手二次换握约 `6.2 s`，以及多个重复求解/等待阶段。

### 2. 习惯性接受、却没有验证过的假设

- 默认相信历史 XML 注释就等价于已按 SDK 对齐，而没有同时检查编译后相机的父 body、世界位置和实际光轴。
- 默认所有 RGB 相机都使用 `70°` 垂直视场；SDK 文档只规定主题和外参，实际内参必须由真机 `CameraInfo` 获取。
- 默认只要简化碰撞槽与成功判定一致，视觉货架不必呈现同一个槽；这对纯动力学测试尚可，对视觉策略训练和人工验收不成立。
- 默认“逐手移动更安全”。旧实现只验证单臂路径，却把双臂任务拆成明显不自然的串行动作；安全应由组合状态碰撞验证保证，而不是由串行本身保证。
- 曾默认架前二次松手、平移 `4 mm`、再夹紧只是历史补丁。后续单变量完整消融已证伪：删除它后，连续后撤 `24 mm` 结束时左右仍各有一个指腹承托棒子，完全脱指硬门拒绝；因此当前保留的是经反例证明的最小必要步骤，而不是继续沿用惯例。
- 默认固定 `azimuth=135°` 的单一自由相机足以同时覆盖桌面和货架。六个关键阶段的同状态回放表明 `azimuth=45°` 对桌面抓取和架前动作的遮挡更少；最终放置仍应另有正常视觉槽近景，而不是只看隐藏视觉网格的碰撞近景。

### 3. 真正想实现的目标

- 生成能迁移到真机传感器配置的示范：机器人先移动并用真实存在的头部/机身相机观察，再以连续、双臂协调、可学习的动作完成水平抓取、运输、低位前送、完全释放和撤臂。
- 同一最终状态必须同时满足三种证据：物理接触成功、正常视觉中明确落入可见槽、机器人相机能观察到任务关键阶段。
- 在不降低四指腹抓持、无碰撞、端点内收、真实槽底支撑、完全脱指和 `0.5 s` 稳定门的前提下，先消除结构性冗余，再争取把时长降到 `60–75 s`；不以高速撞架或隐藏等待换时间。

### 4. 现实资源与约束

- 当前是一张 RTX 4090，适合代码开发、离线轨迹验证和单候选录像；此阶段使用 4/8 卡只会把同一个结构性错误更快复制，不具成本效益。
- 没有真机实时 `CameraInfo` 和实拍标定板数据，因此外参可以按 SDK 原表严格修正，FOV/畸变不能伪装成已经验证。
- 当前头部 pitch 关节在 MuJoCo 转换模型中被焊接，任务头姿必须把光轴和安装位置同时烘焙；不能只改渲染画面而宣称已有可动头部。
- 双臂 IK 有多分支和机械限位；所有同步轨迹必须在组合关节状态下逐段采样碰撞，并继续受 SDK 额定速度和关节限位审计。
- 用户要求断开 SSH 后运行，因此长回合只能通过已验证存活的 tmux 会话执行；模型推理本身不会因 SSH 断开自动继续，tmux 中已经启动的仿真/编码进程会继续。

### 原方案中只在修补表面的部分

1. 用额外物理近景证明一个正常视频中看不见的槽，而没有先消除视觉槽与碰撞槽不一致。
2. 给串行单臂路径继续增加净空点和门，而没有把“双臂同步协调”作为轨迹本身的要求。
3. 只按相机名称和 SDK 主题判断相机正确，没有审计编译后的实际位置、光轴和任务头姿旋转中心。
4. 为释放增加架前逐手二次换握，而没有先验证首次抓取姿态能否直接支持释放。
5. 通过自由相机角度和碰撞近景改善观感，但没有把“正常视觉中棒子由可见槽承托”列为硬验收项。

### 从基本事实重新推导出的新路径

1. 以 SDK 原始外参为唯一来源，修正腰前相机位置/俯角；对任务头俯角同时旋转双目位置与光轴。增加运行时相机父级、位置和光轴审计，并在多视角视频上标出相机名与父链接。`fovy` 明确保留为待真机 `CameraInfo` 替换的假设。
2. 让顶部 U 槽拥有与碰撞体同源、同尺寸、正常可见的视觉几何；正常第三视角、视觉近景和物理近景必须在同一最终状态下共同显示棒子落底。
3. 把观察后的抓取准备改成“拓扑约束下的双臂协调路径”：两臂共享平滑时间参数，但各自保持运输已验证的 IK 分支。右臂必须先绕开 `lifter_pitch_2_link`，左臂使用近似镜像的高位净空；数值 IK 种子只决定解分支，不作为机器人要执行的隐藏姿态。离线和运行时均检查组合碰撞、关节限位、速度和末端残差。
4. 对历史步骤逐项做完整物理消融；当前证据要求保留最小末端重抓和一次连续 `24 mm` 后撤，删除分段停顿、上抬退指和沿棒轴撤指。任何进一步缩时都必须先证明仍能完全脱指，而不是降低接触门。
5. 主第三视角保留遮挡较少的 `azimuth=45°`；最终正常视觉近景使用 `distance=0.72 m, azimuth=-45°, elevation=-50°`，碰撞槽诊断近景使用 `0.72 m, 180°, -60°`。两路角度均由同一成功末态的多角度扫描和完整释放片段回放选择。
6. 只在低分辨率单卡候选同时通过物理、视觉、相机外参和轨迹流畅度门后，再用同一代码运行一次高清 tmux 评审回合；用户批准之前不扩 seed、不建训练集。

### 这条路径成立的前提

- SDK 外参表采用机体标准 `X` 前、`Y` 左、`Z` 上且旋转顺序为 ZYX；相机 link 的 `X` 轴作为光轴方向。该解释已被底盘相机 `-10°` 与当前编译后光轴完全一致地交叉验证。
- 新增可视槽必须与碰撞槽共享数值常量且不改变目标语义；否则只是制造第二套可能漂移的模型。
- 双臂组合路径必须真实无碰撞且能在额定速度内跟踪；若仅静态 IK 可达但动态跟踪失败，不能为流畅度放宽门。允许左右臂因结构和分支不同而不完全镜像，但不允许以碰撞或零净空换取表面上的对称。
- 当前最小末端重抓必须继续提供足够的运输摩擦和直接释放净空；未来只有新的完整消融同时通过完全脱指、槽底接触和稳定门，才能删除。

- **推荐方案**：SDK 真相源相机 + 可视/碰撞同源 U 槽 + 拓扑安全的双臂协调平抓 + 已证必要的最小重抓/连续后撤 + 双第三视角验收。

## 1. 当前任务契约

任务流程是：机器人从自然下垂姿态出发，移动到右侧桌子，抓起横放的棒子，移动到正前方架子，将棒子沿世界坐标 `Y` 方向横置于顶层底槽，完全释放并等待其稳定。

代码中的成功判据为：

| 检查项 | 当前阈值 |
|---|---:|
| 棒子中心相对目标中心的 `X/Y/Z` 误差 | `≤ 3 / 55 / 12 mm` |
| 棒轴与目标轴夹角 | `≤ 10°`，正反向均接受 |
| 棒子必须完整位于架子内宽 | 是 |
| 槽底支撑力 | `≥ 0.5 N` |
| 棒子与真实槽底碰撞几何必须接触 | 是 |
| 棒底到槽底顶面的几何间隙绝对值 | `≤ 2 mm` |
| 双夹爪接触力 | `≤ 0.2 N` |
| 桌面支撑力 | `< 0.5 N` |
| 线速度 | `≤ 0.02 m/s` |
| 角速度 | `≤ 0.10 rad/s` |
| 所有条件连续成立 | `≥ 0.5 s` |

其中“完整位于架子内宽”按四根立柱的真实内侧面 `y=±0.285 m` 判断，并在终局证据中保存棒子正、负 Y 两端的独立余量；任一余量小于 0 即失败。

棒长为 `0.500 m`，架子两侧立柱内的有效宽度为 `0.570 m`，占比 `87.72%`，已经满足要求的 `80%–90%`；理想居中时每端约有 `35 mm` 余量，因此不因透视画面缩短棒子。

SDK 原文列出六个 RGB 成像端点：底盘前 Gemini 2L、腰前 Gemini 2L、头部双目左/右和鱼眼左/右；没有腕部或手部相机。当前模型已对齐其中 `stereo_left / stereo_right / waist_front / chassis_front` 四路，鱼眼尚未建模；策略输入固定为 `stereo_left / waist_front / chassis_front`，`stereo_right` 只作诊断。任何 `hand_left / hand_right` 都只能视为历史仿真诊断视角，不能冒充真机策略输入。

权威实现位于：

- 场景：`Sorting_Roll/sorting_roll_scene.xml`
- 场景生成与检查：`cruzr_mujoco_sim/scripts/core/sorting_roll_scene.py`
- 成功判定：`cruzr_mujoco_sim/scripts/core/sorting_roll_task.py`
- 遥操作与原始录制：`cruzr_mujoco_sim/scripts/core/cruzr_teleop.py`
- SDK 机器可读契约：`cruzr_mujoco_sim/scripts/core/cruzr_s2_sdk_contract.py`
- 单回合物理评审专家：`cruzr_mujoco_sim/scripts/collection/sorting_roll_expert.py`

## 3. 立即可做：采集一个 pilot 原始回合

以下示例会写入 `outputs/teleop/sorting_roll_pilot_000001/`。每个回合必须使用新名称；当前录制器不会拒绝已有目录，重复名称可能混入或覆盖旧数据。

```bash
EPISODE_NAME=sorting_roll_pilot_000001
test ! -e "outputs/teleop/$EPISODE_NAME"

CRUZR_EP_SEED=1 \
REC_PROMPT="Pick up the roll from the table and place it stably in the top shelf slot" \
REC_CAMS=stereo_left,stereo_right,waist_front,chassis_front \
REC_SAVE_RAW_TIMESTAMPS=1 \
TELEOP_RECORD_GPU=0 \
TELEOP_RECORD="$EPISODE_NAME" \
bash Sorting_Roll/run_scene.sh view
```

说明：

- 默认查看器使用 EGL GPU、`1280×720 / 60 FPS`；训练相机按 `640×480 / 30 FPS` 单独录制。
- 键盘焦点必须放在启动命令所在的终端；图形窗口只负责显示和鼠标调视角。
- 不要设置 `TELEOP_HOME=pregrasp` 或 `TELEOP_HOME=sidegrasp`。它们属于旧 `jig` 任务；Sorting Roll 应使用默认 `droop`。
- `CRUZR_EP_SEED` 当前只写入元数据，还不会随机化 Sorting Roll 场景。
- `REC_SAVE_RAW_TIMESTAMPS=1` 会额外保存同步采集时间戳，建议 pilot 也开启。

### 单回合操作顺序

1. 场景打开后，在终端按 `z`，确认出现 `[REC] ● RECORDING ON`，再开始移动机器人。
2. 用底盘移动到右侧桌子并停车；接近物体前保持低速。
3. 调整双臂并夹住棒子，抬起后确认棒子未滑落。
4. 将底盘移动到正前方架子，停车后再执行精细放置。
5. 将棒子沿架子宽度方向放入顶层底槽，打开两侧夹爪并退出接触。
6. 肉眼确认棒子由槽底支撑、不再接触桌面和夹爪，至少等待 0.5 秒。
7. pilot 看起来成功时按 Enter 保存并退出；明显失败时按 Backspace 丢弃整个回合。

第 6 步目前只是人工检查。按 Enter 写出的 `success=true` 不是 `sorting_roll_task.py` 的物理判定结果，所以该回合仍只能标记为 pilot。

不要用 ESC、图形窗口的关闭按钮或终止进程结束有效回合；这些路径不会调用 `finalize()`，可能只留下不完整的 JPG 目录。Backspace 会递归删除当前回合目录，删除后不能从录制器恢复。

## 7. pilot 数据管理规则

- pilot 与正式数据使用不同目录，建议命名为 `sorting_roll_pilot_<六位编号>`。
- 每个编号只使用一次；启动前用 `test ! -e` 检查目标目录不存在。
- 保存失败回合用于分析时，应移入独立 `failed/` 或 `debug/` 区域并写明原因，不能混进成功训练源。
- 不要直接修改 `meta.json.success` 或 `meta.json.task` 来“修复”标签；应由正式采集程序根据物理证据生成。
- 数据、视频和输出目录受 `.gitignore` 管理，不要强制加入 Git。

建议先录少量 pilot，覆盖成功、抓取失败、运输滑落、槽位错位和未完全释放等情况。这里不规定正式条数；正式规模应在成功门、随机化和验收器完成后，根据首批通过率与训练需求确定。

## 8. 正式采集前必须完成的开发

1. 新增 Sorting Roll 专用采集入口，避免依赖旧 `jig` 任务的对象名称、初始姿态和元数据。
2. 将 `evaluate_placement()` 和 `SortingRollSuccessTracker` 接入运行循环；只有物理条件连续满足 0.5 秒才允许写 `success=true`。
3. 每帧或至少终局保存棒子位姿、线/角速度、槽底/桌面/夹爪接触力及各项成功检查。
4. 把任务名、任务版本、采集配置、场景/资产哈希、seed、prompt 和相机契约写入 `meta.json`。
5. 实现按 seed 重置与随机化，至少覆盖棒子初始位姿、机器人初始位姿和合理的视觉/动力学变化；train/val/test 按源 seed 隔离。
6. 新增 Sorting Roll source validator，拒绝空回合、错误任务版本、错误相机、帧数不一致、非有限数组、失败标签和缺少终局稳定窗的回合。
7. 新增或参数化 LeRobot 构建器，明确 16D 关节状态与底盘字段如何组成训练 schema，并通过小数据 canary。
8. 用实测棒子质量替换 `0.25 kg`，重新运行场景、抓取和成功判定测试。
9. 冻结正式相机组合前，确认仿真相机与计划使用的真机相机一致；不得把历史仿真手部相机或未建模鱼眼默认加入策略输入。

正式准入顺序建议为：

```text
场景/资产检查
  → 唯一 seed 和输出目录检查
  → 采集完整回合
  → 物理成功门
  → 数组、时间戳和相机一致性检查
  → 视频抽检
  → 按源 seed 划分 train/val/test
  → 构建 LeRobot 数据集
  → 小规模训练 canary
  → 扩大正式采集
```

## 9. 两天内的成本敏感方案

本节使用以下估算参数：目标为 300 个成功仿真回合，自动专家单次尝试平均 4 分钟，成功率 80%，GPU 按卡时计费。参数只用于规划，正式扩卡前必须用本任务实测值替换。

两天目标指“可通过自动成功门、可构建 LeRobot 并用于短训练 canary 的仿真数据”，不等同于已经完成实物质量标定、完整随机化和 sim-to-real 验证的最终数据。

| 时间 | GPU | 工作及通过条件 |
|---|---:|---|
| 第 1 天，0–10 小时 | 1×4090 | 实现自动专家、reset、录制、Sorting Roll 成功门和正确元数据 |
| 第 1 天，10–14 小时 | 1×4090 | 跑 20 个独立 seed；至少 18 个通过完整物理成功门 |
| 第 1 天，14–20 小时 | 1×4090 | 采集 30–50 个 canary，完成 validator、视频抽检和 LeRobot 加载测试 |
| 第 2 天，0–1 小时 | 4×4090 | 短时并行基准，确认无 seed/目录冲突，吞吐至少达到单卡的 3.2 倍 |
| 第 2 天，1–9 小时 | 4×4090 | 主批次按唯一 seed 分片；达到目标成功数后立即停止并释放额外 GPU |
| 第 2 天，后续 | 1–2×4090 | 只补失败 seed 和尾部缺口；validator、MP4、LeRobot 构建主要使用 CPU/单卡 |

如果自动专家到第 1 天第 14 小时仍未达到 `18/20`，不要扩卡。并行只会更快地产生失败数据，应继续用单卡修复专家，或将两天交付降级为少量人工轨迹加确定性重放的管线 canary；重放变体不能统计为独立专家源。

## 10. GPU 时间与费用估算

定义：

- `N`：目标成功回合数；
- `t`：单次尝试平均分钟数；
- `p`：专家成功率；
- `W`：并行 GPU/worker 数；
- `η`：并行效率，包含 CPU、JPEG 和磁盘竞争。

```text
墙钟小时 = N × t ÷ (60 × p × W × η)
总 GPU 小时 = W × 墙钟小时
预计费用 = 总 GPU 小时 × 每张 GPU 的小时单价
```

以 `N=300`、`t=4 分钟`、`p=80%` 为例：

| 配置 | 并行效率假设 | 预计墙钟时间 | 预计 GPU 小时 | 相对判断 |
|---|---:|---:|---:|---|
| 1×4090 | 100% | 约 25 小时 | 约 25 GPUh | 最省，但批采时间最长 |
| 4×4090 | 90% | 约 6.9 小时 | 约 27.8 GPUh | 多约 11% 卡时，节省约 18 小时 |
| 8×4090 | 75% | 约 4.2 小时 | 约 33.3 GPUh | 比四卡只快约 2.7 小时，卡时再增加约 20% |

如果各卡小时单价相同，增加 GPU 主要购买的是更短的墙钟时间，而不是更少的总费用。对于首批 300 个回合，四卡通常是成本与时间的平衡点，八卡默认不启用。

实际结算还要考虑云平台整机价格、最小计费粒度和多卡折扣。扩卡前应先用单卡实测 `t` 和 `p`，再代入公式，不以表中的 4 分钟和 80% 作为结算依据。

## 11. 何时使用 1、4 或 8 张 4090

| 阶段 | 建议配置 | 原因 |
|---|---:|---|
| 编写和调试自动专家 | 1 张 | 代码、物理和成功门调试不能有效并行 |
| 单回合相机/录制 smoke | 1 张 | 先消除错误标签、视角和输出格式问题 |
| 20-seed readiness | 1 张 | 在扩大费用前获得真实成功率 |
| 30–50 回合 canary | 1 张 | 验证长时间稳定性、磁盘和数据构建 |
| 四卡扩展基准 | 4 张，10–60 分钟 | 只测吞吐、资源冲突和费用模型 |
| 主要批量采集 | 4 张 | 300 回合规模的默认性价比配置 |
| 失败补采和尾部缺口 | 1–2 张 | 防止多卡等待少量任务 |
| 验收、MP4、LeRobot 构建 | 0–1 张 | 通常受 CPU、FFmpeg 和磁盘限制 |
| 8 卡批采 | 条件启用 | 仅在更大规模或硬截止时间下使用 |

四卡必须同时满足以下条件才可开启：

- 20 个独立 seed 至少成功 18 个；
- 连续运行 1–2 小时没有显存泄漏、空回合或非有限状态；
- 每个 worker 使用不重叠的 seed、独立输出目录和正确 GPU ID；
- validator 能自动拒绝失败、缺帧、错相机和错误任务版本；
- 磁盘空间足以容纳目标批次，持续写入不会拖慢仿真；
- 四卡短测吞吐至少达到单卡的 3.2 倍。

只有满足下列任一条件，且八卡实测并行效率仍不低于约 80%，才考虑 8 卡：

- 目标扩大到 600–1000 个以上成功回合；
- 单回合实测超过 6–8 分钟；
- 四卡按实测速度无法在硬截止时间内完成；
- 需要同时采集多个相互独立的随机化 profile；
- 云平台的八卡整机存在足以抵消并行损失的价格折扣。

### 降低费用的执行规则

- pilot 阶段保留四路已建模的 SDK 对齐相机用于确定视野；冻结策略输入后，正式批采只录三路策略相机，可比四路减少约 25% 图像渲染和写盘。全景与槽位物理近景只按抽检比例生成。
- 抓取失败、棒子掉落或发生不可恢复碰撞时提前终止，不跑完整超时。
- 目标 300 个成功回合时，先把最大尝试数限制在 400–450；达到成功数立即全局停止。
- 采集过程中不为每个回合生成 MP4，只审查全部失败回合和约 10% 成功回合。
- 四卡按成功目标分片，而不是按固定运行时间；例如 300 个目标可先分配每卡 75 个，并由协调器处理尾部差额。
- 额外 GPU 只在四卡基准和主批次期间租用；数据验收、视频编码、数据集构建和失败分析开始前立即释放。
- 如果四卡吞吐不足单卡的 3.2 倍，先处理 CPU、JPEG 或磁盘瓶颈，不扩到八卡。

## 12. 当前不要执行的操作

- 不要直接运行 `shelf_e2e_batch.sh` 或 `shelf_e2e_multigpu_collect.py` 采集 Sorting Roll；它们使用双物料专家和双物料成功门。
- 不要用 `shelf_e2e_source.py` 或 `shelf_e2e_build_v2.py` 验收/构建 Sorting Roll；任务版本、阶段和质量契约不匹配。
- 不要从 `scripts/archive/` 选择旧转换脚本作为新正式流程，除非先逐字段验证并显式改造成 Sorting Roll 专用实现。
- 不要把人工看到“差不多放进去了”当作成功标签；正式标签必须来自 `sorting_roll_task.py` 的完整稳定判据。

## 13. 常见问题

### `view` 提示找不到 Python

```bash
RL_MJX_PY=/path/to/mujoco/python bash Sorting_Roll/run_scene.sh view
```

### EGL 窗口启动失败

可先指定 GPU：

```bash
TELEOP_EGL_GPU=0 TELEOP_RECORD_GPU=0 bash Sorting_Roll/run_scene.sh view
```

仅做兼容性查看时可回退 CPU viewer；正式多路相机录制仍需要 EGL：

```bash
TELEOP_VIEWER=passive bash Sorting_Roll/run_scene.sh view
```

### 目录中只有 JPG，没有 `meta.json` 或 `episode_data.npz`

该回合没有正常 finalize，通常由关闭窗口、按 ESC、异常退出或强制终止造成。把它视为不完整回合，不要进入数据集；使用新编号重新采集。

### 按键没有反应

把焦点切回启动命令所在的终端。每次有效按键都应看到 `[KEY]` 回显。

## 14. 当前推荐决策

先用当前单张 4090 完成场景检查、少量人工 pilot、自动专家开发、20-seed readiness 和 30–50 回合 canary。只有成功率、validator、磁盘和四卡吞吐门全部通过，才在第二天短时租用另外三张 4090 进行主批次；达到目标后立即释放，失败补采和收尾恢复单卡。首批 300 回合不使用八卡，除非四卡实测无法满足硬截止时间且八卡并行效率通过基准。
